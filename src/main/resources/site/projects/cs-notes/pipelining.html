Pipelining

In this set of notes, the concept and various implementations of instruction pipelining are presented. Instruction pipelining, often simply referred as pipelining, is a performance enhancing technique first appeared in electronic computers around the early sixties in commercial projects such as the IBM 7030 Stretch being one of the most notable ones. It was then heavily adopted in the late seventies in supercomputers, such as the Cray-1 and later on CISC oriented machines in the mid-eighties.

1. Baseline

The following is a high-level diagram of a simple RISC-like processor microarchitecture without pipelining, which will serve as the baseline throughout this and subsequent set of notes.

Assume the following for the baseline implementation:

  • Instruction memories, data memories and registers are all asynchronous-read and synchronous-write for simplicity.
  • All instructions take 1 cycle to resolve for simplicity (no multistep or microcode).
  • The instruction memory is read only.


In this basic microarchitecture, each instruction goes through the usual processing phases: fetch, decode, execute, memory access and write-result all in a single cycle, thus resulting in an IPC (instructions-per-clock) of 1. The clock period, however, must be long enough to allow the execution of all the phases in a single cycle, effectively placing all the circuitry in series with one another, resulting in a long combinatorial path. This is a major performance bottleneck, which can be significantly improved without modifications to the component themselves, by implementing instruction pipelining.

2. Concept and application

To understand the general concept of pipelining, we can take a look at a car production pipeline as an example. In order to build a car, we have to put together a series of components such as: the engine, clutch, transmission, the chassis, suspensions, wheels and many more. In a hypothetical scenario, let's say that building a single car takes 1 day. The production flow might be something like the following:

  1. Build the chassis.
  2. Paint it.
  3. Mount the engine.
  4. Mount the transmission.
  5. Mount the clutch.
  6. Mount the suspensions.
  7. Mount the interiors.
  8. Mount the wheels.
  9. Done.


If those steps are executed in series and no new car can be built until the current one is complete, then it's easy to see that the throughput of the production line is 1 car per day. In reality though, it's possible to have multiple cars being built on the same production line because once the chassis of car X has been built, it will move to the painting step. This means that the equipment for building chassis is sitting idle when it could be building the chassis for the next car X+1. Since all steps are independent, we can apply this logic to all production stages, which allows several cars to be built in "parallel" with each in a different stage.

With this, the time it takes to build a single car stays the same, but the throughput increases by the number of stages that the production line has: 8 times in this example, so 1 car every 3 hours. When a car exits the production line, soon another one that was one stage behind completes and exits the pipeline. In short, this technique exploits "temporal" parallelism by reutilizing as much of the already existing equipment as possible.


This concept can be applied to logic circuits too, including CPUs because instructions go through different independent steps just like the car production line example. In order to make the processor pipelined, we need to divide each step boundary with a pipeline register creating a single pipeline stage. This register is a single line of d-type flip-flops that stores the result of the stage associated to it, this way, the stage is free to handle the next input without losing information. We place these registers at the end of each stage forming something that vaguely resembles a gigantic shift-register.

Just like the car example, the time it takes to execute a single instruction is the same (in reality though, it's slightly longer due to the pipeline registers which add small delay due to their setup and hold times). However, it now becomes possible to drastically decrease the clock period because the amount of "work" that needs to be done per stage is much lower, which means that the combinatorial path of each individual stage is shorter, thus increasing the overall throughput.


An important observation is that, even though the processor executes multiple instructions per cycle, those instructions are all at different stages which has no effect on the overall IPC, which stays at 1, like the initial non pipelined version. We can prove this intuitively by calculating the number of cycles it takes to execute a program composed of 1 instruction, then one with 2, then one with 3 and so on. For example, assume that the pipeline has 5 stages: fetch, decode, execute, store and writeback

  • 1 instruction: 5 cycles (IPC = 0.2).
  • 2 instructions: 6 cycles (IPC ~ 0.33).
  • 3 instructions: 7 cycles (IPC ~ 0.43).
  • 4 instructions: 8 cycles (IPC = 0.5).
  • 1000 instructions: 1004 cycles (IPC ~ 1).


The more instructions are executed, the closer the IPC approaches 1 and, since programs execute billions of instructions, the IPC very quickly reaches 1.

3. Dependencies and hazards

Up until now, we have assumed that instructions are independent of one another and this assumption has been the foundation that allows pipelining to work. In reality, however, this is not really true... and it's a big problem because it can, in the best case, lead to degraded performance and in the worst case to straight-up incorrect execution. To understand why dependencies between instructions can cause issues, we firstly have to define what exactly they are. Dependencies are divided into three main categories:

  • Data dependencies.
  • Control dependencies.
  • Structural dependencies.


It's important to note that dependencies are a property of a program and not of any particular microarchitecture, pipelined or not. On a given microarchitecture, however, such dependencies can lead to incorrect execution and, when they do, it's referred to as a hazard and they must be avoided and/or handled in order to correctly execute any given program.

3.1. Data dependencies

Data dependencies define how the data flows through the program and dictate how it computes. They can be further divided into three subcategories:

  • RAW (read-after-write) dependencies. These are also sometimes called true dependencies or flow dependencies because they define how the program computes and manipulates data. They cannot be removed and must always be obeyed.
  • WAW (write-after-write) dependencies. These are also sometimes called output dependencies because they specify what should be the final value of something. For register-to-register dependencies, these often exist because there might only be a limited number of registers available to hold variables.
  • WAR (write-after-read) dependencies. These are also sometimes called anti dependencies because it can be thought as the reverse of the RAW dependency.


For this class of dependencies, we will use register-to-register data dependencies for illustrative purposes as it's simpler to reason with them, but they are not exclusive to registers. It's entirely possible, to have data dependencies between register and memory operations and even between memory operations themselves, but the underlying logic is always the same. Take the following code snippet as example:

# Syntax: [operation]: [destination], [operand 1], [operand 2], ... [operand n]

1. ADD: r1, r2, r3
2. SUB: r4, r1, r5
3. MUL: r1, r6, r7

There are 3 data dependencies in this snippet: a RAW from line 1 to 2, a WAW from line 1 to 3 and a WAR from line 2 to 3 all targeting register 1. The RAW dependency is present because the SUB must wait for the ADD to finish before it can go, because one of its inputs depends on the result produced by the ADD. The WAW dependency is present because the program demands that the last value of register 1 should be the one produced by the MUL. In this specific example, the MUL and the ADD could swap places without affecting execution, but this is only a simple snippet and in a real program the MUL might feed subsequent instructions. It's easy to see now why the WAW dependency is also called output dependency, and it's because it dictates what the last output of a particular variable (register or memory location) should be. Finally, the WAR dependency exists because the MUL should not be allowed to overwrite register 1 before the SUB has finished reading it, because that would lead to incorrect execution of the program.


In short, data dependencies dictate what orderings of instructions are legal.

3.1.1. Handling data hazards

As mentioned earlier, dependencies can potentially transform into hazards on microarchitectures that go beyond the baseline that we have defined earlier. For simple in-order scalar microarchitectures, that is, microarchitectures that execute instructions strictly in program order and process a single instruction per stage, the RAW dependency is the only relevant one. The WAW and the WAR are automatically satisfied by the pipeline itself, simply because it executes 1 instruction at a time in the order that they appear in the program.

To understand how the RAW hazard can manifest itself in a simple pipeline, we can take the naive 5-stage pipelined microarchitecture that we discussed earlier. If we try to execute the code snippet we run into a problem... When the ADD is in the execute stage, the SUB is in the decode stage, which means that it's also reading the registers. This is problematic as the SUB will latch the old value of register 1 at the end of the cycle before the ADD had a chance to save its result. In fact, this issue will persist even with two independent instructions in the middle of the ADD and the SUB. With a separation of three or more cycles, the hazard is automatically resolved because the SUB will be in the fetch stage (or not even in the pipeline at all) when the ADD is writing the result into the register file. There are different ways to handle this situation each with its positive and negative aspects:

  1. Place no-op instructions between the ADD and the SUB at the program level. This requires no changes to the hardware, but it severely lowers performance and the program will be microarchitecture-dependent instead of just ISA-dependent, which is also a severe compatibility drawback.
  2. Reorder independent instructions to fill the gap. Better than option 1, but it still has the same compatibility drawback as the first option and is not always practical to perform. Compilers have a limited "window" of instructions that they can examine, and they might not find any instruction suitable for reordering.
  3. Inject no-op instructions between the ADD and the SUB at the hardware level. This requires changes to the hardware because the processor must be able to detect when a RAW hazard is going to happen and that might slow down the critical path. It's still suboptimal for performance, like the first two options, but it solves the compatibility drawback.
  4. Forward the value produced by the ADD directly into the execute stage without waiting for the write event to the register file or injecting any no-op. This is the best option as it has no performance impact (when applicable) and, like option 3, it has no compatibility drawbacks. It requires, however, significant hardware changes and may slow down the critical path.

3.1.2. Forwarding

Forwarding is a technique that consists in feeding the dependant instruction the result produced by an earlier instruction X before X has written the result into the register file. To do this, the CPU needs to detect when a conflict will happen between two instructions and "bypass" the correct result when appropriate. In practice, forwarding implementations consist of:

  • Forwarding-unit: a dedicated hardware structure, usually placed in the decode stage (the stage where registers are also read), that compares the source registers of the instruction in the decode stage, with the destination registers of earlier instructions in order to activate the various bypass paths.
  • Bypass multiplexers: multiplexers that feed the correct value to the desired functional units. With the 5-stage pipeline as the example: either in the execute stage to the ALU, and/or to the data memory inputs.
  • Bypass buses: paths that feed the stage result back to the bypass multiplexers.
  • Stall logic for when forwarding cannot be applied. This logic effectively injects no-ops, creating a pipeline bubble, delaying and padding execution until the time is right to use forwarding.

3.2. Control dependencies

Control dependencies define the control-flow of the program itself and they arise from control-flow instructions, such as conditional branches, jumps, function calls and function returns. This is because every time the program executes an instruction that changes the control-flow, all subsequent instructions become dependent on it. To complicate things further, branches cause the processor to conditionally execute blocks of code depending on the condition that it checks, which causes a hazard only when the condition is true. To see more clearly, take the following snippet as example:

# Syntax: [operation]: [destination], [operand 1], [operand 2], ... [operand n]

  1.  ADD: r1, r2, r3
  2.  BEQ: r1, r2, @label
  3.  ADD: r2, r3, r4
  4.  SUB: r4, r5, r8
@label:
  5.  DIV: r6, r7, r9
  ...

Depending on the outcome of the branch, either lines 1 through 4 or line 44 onwards are executed depending on if register 1 and 2 are equal. This can be problematic because if the branch condition is true, then the pipeline might potentially be filled with the instructions from the wrong path. In that case, the erroneous instructions must be "flushed". If the branch condition is false, however, then those instructions are indeed the correct ones and no hazard is generated.


To flush the erroneous instruction, all that is needed to do is to block such instructions from altering any stateful component. Doing so, will effectively transform those instructions into no-ops that travel along the pipeline.

Simply put, every time an instruction causes the program-counter to not go to the next instruction, but to jump somewhere else, it will generate this hazard.

3.2.1. Handling control hazards

There are different solutions for handling this type of hazard, many of which are similar to what we saw earlier for data dependencies:

  • Place no-op instructions after every branch at the program level. This option does not require any hardware changes, but it severely lowers performance and the program will be microarchitecture-dependent instead of just ISA-dependent, which is also a severe compatibility drawback.
  • Inject no-op instructions after every branch at the hardware level. This requires changes to the hardware because the processor must be able to detect a potential control-flow change during the fetch stage. It's still suboptimal for performance, like the first option, but it solves the compatibility drawback.
  • Reorder instructions to fill the gap at the program level. The pipeline has a number of stages before the EX stage, which is usually where the control-flow instructions are resolved. Those stages, also referred as delay slots, can be filled with instructions that come after the if-then-else statement and will always be executed unconditionally. This strategy has two drawbacks: one is the compatibility issue that options 1 and 2 have, the other is that it's not always practical or possible to find suitable instructions to fill the delay slots.
  • Speculation: implement circuitry that tries to predict what the outcome of a control-flow instruction will be, in order to minimize the chance of getting the hazard.


The following is an example of the branch delay slot filling strategy mentioned above. The first snippet uses the first option, while the second is rewritten by taking advantage of the delay slots:

# Unoptimized snippet
# Syntax: [operation]: [destination], [operand 1], [operand 2], ... [operand n]

@loop:   1.  LDB: r1, r2, #0
  2.  ADI: r3, r3, #1
  3.  ADI: r2, r2, #1
  4.  BNE: r1, r0, @loop
  3.  NOP
  3.  NOP
@continue:   
...
# Optimized snippet
# Syntax: [operation]: [destination], [operand 1], [operand 2], ... [operand n]

@loop:   1.  LDB: r1, r2, #0
  2.  BNE: r1, r0, @loop
  3.  ADI: r3, r3, #1
  4.  ADI: r2, r2, #1
@continue:   
...

The two snippet implement a very simple C-like string length calculation (in this example it also includes the null-character in the length). They are composed of a loop that loads a byte from memory at the address referenced by register 2 into register 1. They then increment the appropriate counters and finally check if the fetched character is the null-character with a "branch if not equal" instruction (assume that register 0 is a constant value of 0, which is what the null-character is). If the condition is true, then the loop hasn't reached the end and continues, otherwise it exits. The second snippet replaces the NOP instructions with the ADI ones while keeping the overall behavior unchanged. As explained, this is because the 5-stage pipeline has 2 cycles worth of delay slots, therefore, by the time the branch is resolved, the ADI operations are in the pipeline and will always execute unconditionally.


Speculation, also called branch prediction when it comes to control-flow, is the best way of handling control-flow dependencies, and it's what modern processors employ. It doesn't guarantee to completely eliminate them (as that is practically impossible), but it will reduce the chance of a hazard, and thus, the performance penalty associated with it without modifying the program. There are many ways of implementing this option, and they will be explored in detail in subsequent sets of notes, but for now, the simplest approach is to implement the "always-not-taken-predictor", which simply keeps fetching the next instruction normally and flushes when the hazard happens.

3.3. Structural dependencies

Structural dependencies are an extremely pervasive type of dependency and exist any time an instruction uses a "resource", which can be things like a functional unit like an ALU, register read/write ports and other things. This type of dependency does not usually result in a hazard for simple pipelines such as the ones presented here. They can be problematic in more advanced CPUs that execute many instructions per stage, for example: in a pipeline that executes 4 instructions per stage (4-wide), there might be 4 ALUs, but maybe only one divider. If there are 2 or more divide instructions that can be executed in parallel, then a hazard might arise simply because there is only one divider available. A similar issue can present itself when it comes to register read and write ports: a CPU that can execute many instructions per stage, must also have a register file that allows reading many operands concurrently, which is expensive in terms of chip area and power. As an example a 4-wide pipeline might have a register file with 8 read ports and 4 write ports. This CPU might also support instructions that read 3 operands instead of the standard 2, which would require a total of 12 read ports in the worst case. This is over the limit of 8, so a structural hazard will occur in this case, resulting pipeline stalls.


There isn't really a solution to this type of dependency, other than to equip the pipeline with enough resources to give good performance under a variety of different conditions.

3.4. Complete example

The above example diagram is a "complete" pipeline with an extensive and aggressive forwarding approach and the basic "always-predict-not-taken" branch predictor. There are several forwarding paths, which cover all possible cases:

  1. Register-register cases: all handled via the bypass multiplexers on both ALU inputs in the EX stage. Two are required because classic RISC-like architectures employ 3-operand instructions that read up to 2 sources. The bypass multiplexers are controlled by the forwarding-unit via outputs fwd-2 and fwd-3.
  2. Memory load to memory load: the only possible dependency is on the address, that is, the first operation loads a value from memory that will be used by the second operation as part of the address calculation. In this case, it's not possible to forward without stalling because when the second load is calculating the address with the ALU, the first one doesn't even have the value yet. The solution is to stall the IF, ID and EX stages for one cycle to allow the first load to proceed. After that, it's possible to use the already present bypass paths to forward the correct value to the second load.
  3. Memory load to memory store (on data): handled via the bypass multiplexer on the data-in input in the memory stage, controlled by the fwd-1 on the forwarding unit. This hazard can also be partially solved without the additional bypass path, but requires stalling the IF, ID and EX stages for one cycle when the store is in the EX stage.
  4. Memory load to memory store (on address): same case as 2.
  5. Memory load to register instruction: same as case 2.
  6. Register instruction to memory load: same as case 1.


To avoid forwarding on inappropriate instruction sequences, the forwarding unit has 3 "inhibit" inputs taken from the EX, ST and WB stages. This is to avoid forwarding bogus data from instructions that don't actually produce a result, like control flow instructions. This "misfire" might happen due to the raw instruction encodings:

The first instruction format might encode for a JMP instruction and the second one for an ADD instruction. If the program has the following sequence of instructions:

# Forwarding misfire
# Syntax: [operation]: [destination], [operand 1], [operand 2], ... [operand n]

  1.  JMP: #0x30000000
  2.  ADD: r1, r3, r2
...

A naive forwarding unit will incorrectly issue a forward on the src1 for the ADD, which would be wrong. This is because the forwarding unit simply compares for equality fixed bits from the incoming instruction.

4. Closing remarks

Instruction pipelining is a complex topic that has many intricate details, rules and exceptions. The point of this writing is to lay down the basics and some of the most notable issues and solutions. This space is dedicated to some additional remarks, under the form or a Q&A.

Is the read-after-read (RAR) dependence a thing?

No, not in the "usual" way. That's because two instructions that read the same thing without anyone else interfering, can be reordered without resulting in incorrect execution. Instructions that have side effects, such as modifying one of the source registers (or some other stateful resource) can be modeled as a hidden RAW dependence.


There are more complex and obscure dependencies, that don't have a dedicated name, but they involve advanced CPUs with multiple cores, caches and Out-of-Order execution. Those techniques, when combined, can result in some nasty behavior in certain cases (which will be explored in subsequent sets of notes).

What about self-modifying code?

That is another issue... in the proposed examples, the instruction memory is treated as a ROM that cannot be changed, which renders this question moot. However, if we did allow this feature, the proper way of modeling this would be with a RAW dependence on the instruction memory itself. Since self-modifying code is not something that happens very often (from the point of view of the CPU itself), it's fine if no-op instructions are placed after the modifying operation to resolve the hazard. Alternatively, but it's a bit excessive, it would be possible to have a bypass path from the instruction memory in the ST stage into the input of the control unit, thus, eliminating the need for the no-ops.

How many stages should a pipeline have?

Not an easy question to answer as it depends (as always). A picture is worth a thousand words:


Performance gains become smaller and smaller because the time that the pipeline registers take to latch the values becomes more and more dominant. At the same time, more stages means more hazards and a higher clock speed means higher power usage.


In the end, hard to say. There have been CPUs with a very deep superpipeline (when a pipeline has "a lot of stages", it's usually called superpipeline) such as the final revision of the Pentium 4 (Caedar Mill) with 31 stages. More modern CPUs have fewer stages, for example, Intel's Kabylake had 14. The most appropriate answer, I would say, is to aim for the least number of stages that achieve the desired target clock speed.

Some pipeline stages can be faster than others

Up until now, we have assumed that all stages in a pipeline take the same amount of time to perform their function, but this is rarely the case... usually the clock speed will be tailored for the slowest stage, but it's possible to "rebalance" the stages a bit, by using clock offsets. If a stage A takes 10ns to complete and B takes 8ns, it's possible to delay B by 1ns with respect to A, balancing both stages at 9ns. The reason why this works, is because A timings "spill over" to the next stage by 1ns, allowing it to run "late", while B is fast enough to recoup the deficit.
